## Firmware and service behavior

- Supported QIDI Max 4 stock comparisons use `https://github.com/thelegendtubaguy/Qidi-Max4-Defaults`; QIDI Plus 5 comparisons use `https://github.com/thelegendtubaguy/Qidi-Plus5-Defaults`.
- Firmware identity is exposed in `/home/qidi/update/firmware_manifest.json` at `SOC.version`.
- **Runtime-confirmed:** [GitHub issue #71](https://github.com/thelegendtubaguy/valve-oil/issues/71) reported firmware `01.01.06.04` with `/home/qidi/klipper/klippy/extras/homing.py` SHA-256 `0310d9ed0a838b2a7ecff8cd2ec15488b1ae3d8f165a458addd16d8366a60761`. - Unresolved: `Qidi-Max4-Defaults` firmware snapshots currently contain `config/` and do not establish which `01.01.06.04` distribution or update path supplies each `homing.py` variant.
- QIDI firmware packages can replace `/home/qidi/QIDI_Client`, restore animated touchscreen assets, and enable/start `algo_app.service`; opted-in system hardening therefore requires reconciliation rather than one-time migration.

Direct filesystem state and the exact firmware install path remain unresolved.
- Firmware `01.01.06.04` exposes the touchscreen through `qidi-client.service` with executable `/home/qidi/QIDI_Client/bin/qidiclient`.
- Firmware `01.01.06.04` exposes AI detection through `algo_app.service`, executable `/usr/local/bin/algo_app/main`, and port `9010`; the observed `/version` response reported `sw_version=1.1.0`.
- Observed `/config` flags were false for general detection, spaghetti detection, foreign-object detection, and related checks on the captured machine.

All four captures reported zero errors and overflows.
- **Unresolved:** QIDI's [Max4 Adapter Plate product photo](https://us.qidi3d.com/products/max4-adapter-plate) depicts an `A-9(GD) V1.5` board with a footprint labeled `RESET`. The operator reports unpopulated pads rather than a fitted button on the installed board. The pad connections and bootloader entry without a running application remain unverified.

- **Runtime-confirmed:** an operator-supplied read-only dump from a second `01.01.07.01` printer contained the stock THR application above with a different 32 KiB bootloader, SHA-256 `31f8344db7b091df5429960bc9cd06065e2188c3b8092e43fb65eb3f2833723c`. The installer refused it before reset. Its code spans 7,881 bytes against 7,164, its initial stack pointer is `0x200030d0` against `0x20008000`, and all four code pages differ; the only shared run of 32 bytes or more is a 512-byte reflected `0xA001` CRC16 table. Its flash holds `0x00` from `0x080108f0` through `0x08010bff`, the unused remainder of the stock image's final 1,024-byte data packet, where the first board reads erased.
- **Static-recovered:** the second build enters at `0x08001dc0`, initializes C data at `0x08001cdc`, and runs its receive dispatcher at `0x0800014e`. USART1 receive handling is at `0x08000ca6`, UART output at `0x08000c74`, header parsing at `0x08000580`, CRC validation at `0x08000684`, and command handling at `0x08000200`. An identity request with payload `0100` returns payload `0102`, not the first build's `01020102`; it does not expose the first build's four-byte model/version form.
- **Static-recovered:** bounded execution of the second build's actual parser, erase loop (`0x08000960`), and programming loop (`0x080009d2`), with flash-controller/UART/jump operations stubbed, erases the same 48 two-KiB application pages. Each accepted data packet programs 1,024 bytes, zero-padding a short packet; the captured final-packet remainder matches this result. Start/end replies are `0101`/`0201`, and data replies echo the packet index and byte count with status `01` (accepted) or `02` (CRC failure). Duplicate packet zero writes again and advances the destination; later duplicate indices acknowledge without writing.
- **Static-recovered:** the second build initializes its startup counter to 4,000 one-millisecond SysTicks, then waits another 1,000 ticks before its application jump at `0x08000aac`. An identity exchange refreshes the session counter to 10,000 ticks, followed by the same 1,000-tick exit delay, without erasing the application. A data-session timeout instead erases the first application page, waits 1,000 ticks, and requests a system reset at `0x08000130`. A cold start can jump into a partially programmed application. Emulated counter durations are not live wall-clock measurements or proof of power-loss recovery.
- **Static-recovered:** the second image's occupied bytes consist of vectors, code, literal/CRC tables, C initialization records, and constants, followed by erased flash. Inspection found no unique-ID reads, device-derived bootloader data, or bootloader-region writes in the supported transfer call paths; the exact SHA-256 is treated as a build identity, not a hardware identifier. An independent matching board capture has not been obtained and is not required for this static conclusion.
- **Static-recovered:** timed bounded execution of the second build, with its 1 ms SysTick driven from the host's clock (`scripts/check_thr_recovery.py`), refines its session behavior. Every parsed packet, answered or not, reloads the 10,000-tick session counter. After a data-session timeout erases the first application page, packets in the following 1,000-tick exit delay are still acknowledged, but the reset follows regardless, and an end command there jumps at once into the page-0-less application. After a reset, identity and start are answered for the whole 5,000-tick startup period, but only an identity+start received in the first 4,000 ticks keeps the bootloader resident; in the last 1,000 it answers normally and still jumps. Start without a preceding identity is ignored. Identity inside any session gets no reply and only reloads the counter; an identity-only session that expires jumps rather than resets. Start inside a data session is a silent no-op before the first data packet, but after data packets it is answered and erases again without rewinding the write position, so a restarted image lands offset. Across 133 injected faults (dead link or lost replies, 0.5–40 s, at start, packets 0/1/17/34, and end), `Bootloader.transfer` ended with an unusable application in 92 runs, 78 of them while the link was usable inside a rescue window; `transfer_recovering` ended unusable in 20, all with the link dead through the whole window. With the bootloader's SysTick 3% slower than the host, a start acknowledged during the exit delay was mistaken for a new session and the board was left unusable; requiring an identity reply until a slow clock must have reset removed those cases, and the 3 s and 12 s faults at 0.92–1.1× the host clock end with no unusable application. Emulated counters are not wall-clock measurements, flash-controller and UART timing are stubbed, and no recovery path has run on hardware.
- **Runtime-confirmed:** a QIDI Q2 THR board (`A-10 V1.1.3`) with the stock application above and the second bootloader build was probed (reply `0102`, application returned, complete readback unchanged), then programmed with the patched image by `transfer --reset --recover-to-stock`. The transfer completed with no recovery event; after twelve seconds, complete application readback matched `9d2360ba47ebd720dbef07a0a4ebaf26004360bca090997d7b4a118c41460ac9` and the bootloader hash was unchanged. Klipper returned to ready with THR still reporting `02.02.01.08`. A five-second stationary capture delivered `1597.5` samples/s with no gap above one sample period, against `387.6` samples/s before.
- **Runtime-confirmed:** the second board's identity-only run after application reset returned CRC-valid payload `0102`, matching the recovered profile, and the application returned with a reported upper bound of `12.34 s`. The complete bootloader and 35,056-byte stock application hashes matched the original capture before and after the run; bytes beyond the image were not part of this comparison. No firmware was programmed, previously active services were restored, and Klipper was ready with THR connected and all heater targets zero, without a recovery action. A stationary capture delivered `385.58` samples/s with zero errors and overflows.
- **Unresolved:** flash-controller electrical behavior under an interrupted transfer, and every recovery path, remain unexercised on hardware; programming remains subject to installer backup and full readback verification. Physical recovery entry, actual MCU vendor/part, and production-build distribution remain unverified.
- **Static-recovered:** released `qidiclient` SHA-256 `b5285d1a52f1180757360d0893f0f8ed619aaaa31d2d621917c0a963bc3fde4e` stages THR at entry `0x71a9f0`, dispatches component updates at `0x755810`, and transfers firmware at `0x9b02d0`. ## Late commands on the mainboard

- **Static-recovered (`QD_MAX4_MCU_02.01.01.12_20260609.bin` from `01.01.07.01`, SHA-256 `65405946b4b0c152d9115e06d082bc3818b13b5a878970c8a18388a641d510fd`, the same image as Plus 5 `01.01.02.01`; `CLOCK_FREQ` 168 MHz):** `sched_add_timer` (`0x08008610`) does not shut down with mainline's `Timer too close`. A timer added with a wake time already past is moved to the current time plus 2 ticks, runs at once, and emits `output("Timer too close, orig=%u waketime=%u tl->waketime=%u")` at most once a second, where `orig` is the requested clock and `waketime` the MCU's current clock. `Rescheduled timer in the past` and `Move queue overflow` are likewise `output()` messages, not shutdowns. The Box firmware has no lateness check at all; see [Box MCU firmware](qidi-box/mcu-firmware.md#shutdown-reasons).
- **Config-confirmed:** Max 4 `01.01.07.01` `stepper_enable.py` sets `ENABLE_DELAY_TIME = 0.300`. `EnableTracking.motor_enable(print_time)`, which runs when step generation reaches a disabled stepper's first step and for `SET_STEPPER_ENABLE ENABLE=1`, computes `enable_time = max(0., print_time - ENABLE_DELAY_TIME)`, passes it to the enable callbacks and the enable pin, and logs `ENABLE delay: stepper=%s enable=%.6f move=%.6f`. Nothing keeps `enable_time` after the MCU's current time. Plus 5 `01.01.02.01` enables at `print_time`, as upstream does.
- **Config-confirmed (stock `chelper/serialqueue.c`):** a queued command is not sent until the MCU clock expected at its arrival reaches its `minclock`, and `MCU_digital_out.set_digital` sends each change with `minclock` set to the pin's previous change. A pin change scheduled before that previous change therefore reaches the MCU late even when it is still ahead of the MCU's current time.
- **Runtime-confirmed (Max 4 test printer `klippy.log`, 2026-10-31 to 2026-11-07, `01.01.07.01`):** 41 `Timer too close` lines. 37 fell between the `ENABLE delay: stepper=stepper_x` and `ENABLE delay: stepper=stepper_y` lines of X/Y homing, after both stock `kinematics.cfg` and the optimized `homing.cfg` disable X and Y with `SET_STEPPER_ENABLE ... ENABLE=0` and a short `G4` before `G28.6245197`. The first homing move then started about 160 ms ahead of the MCU, so the enable was scheduled about 138 ms in the past. Z enables after `SET_KINEMATIC_POSITION` were scheduled 30–45 ms in the past.
- **Unresolved:** the source of the other four, at 2026-11-02 05:22:26, 10:43:57, and 20:00:08, and 2026-11-03 04:10:16. ### Controlled root-mount measurements

Measurements used Linux `5.10.160`, Python `3.9.2`, and ext4 with `19,766,173,696` bytes available. `qidi-client.service`, `klipper.service`, and `moonraker.service` were inactive for every trial. Each mode used one excluded warm-up and five measured trials. Batch writes include a final `fsync`; metadata timings include directory `fsync` after creation and deletion.

| Workload | `sync` median (range) | asynchronous median (range) | Latency reduction | Speedup |
|---|---:|---:|---:|---:|
| 512 × 4 KiB writes, 2 MiB total | 1510.856 ms (1478.720–1541.888) | 56.153 ms (55.003–56.659) | 96.3% | 26.91× |
| 8 × 256 KiB writes, 2 MiB total | 74.072 ms (71.087–78.555) | 49.573 ms (48.481–51.603) | 33.1% | 1.49× |
| 64 × 4 KiB writes with per-write `fsync` | 203.015 ms (185.096–218.513) | 192.629 ms (177.627–197.354) | 5.1% | 1.05× |
| Create and remove 64 files | 706.394 ms (669.849–711.707) | 96.790 ms (91.821–101.043) | 86.3% | 7.30× |

The 4 KiB batch increased from `1.324 MiB/s` to `35.617 MiB/s`; the 256 KiB batch increased from `27.001 MiB/s` to `40.345 MiB/s`. The per-write `fsync` control changed by 5.1% because both modes explicitly requested durability for each write.

## Touchscreen display and input

- **Runtime-confirmed:** on one Max 4 running `01.01.07.01`, `qidiclient` (root, pinned to CPU 0) holds `/dev/fb0` and `/dev/input/event0` open. `/dev/fb0` is `rockchipdrmfb`, 800×480 at 32 bpp with red at bit offset 16 (XRGB), stride 3200, and virtual size equal to the visible size. It is `root:video` mode `0660`; `/dev/input/event*` are `root:input` mode `0660`, and the `qidi` user is in `video` but not `input`.
- **Static-recovered:** `qidiclient` contains LVGL display and input driver registration symbols and the string `/dev/input/event0`.
- **Runtime-confirmed:** `event0` is `Goodix Capacitive TouchScreen` (`INPUT_PROP_DIRECT`), reporting `ABS_X`/`ABS_Y` and `ABS_MT_POSITION_X`/`_Y` over 0–799 and 0–479, slots 0–4, tracking IDs up to 65535, and `BTN_TOUCH`. `event1` is a USB button device.
- **Runtime-confirmed:** capturing `/dev/fb0` as `qidi` produced the displayed screen. Writing slot-0 multi-touch events with `BTN_TOUCH` and single-touch axes to `event0`, then a release, pressed the touchscreen at the written screen coordinates: a press at (40, 335) opened the Settings tab and (40, 45) returned to Home.
- **Runtime-confirmed:** a press and release written to `event0` within a few milliseconds of each other was ignored, while the same press held 80 ms was acted on. `qidiclient` appears to act on the final state of the queued events it reads, so very short presses are lost.
- **Runtime-confirmed:** on that host (RK3308, four cores, 486 MB RAM), a full framebuffer copy through `mmap` took about 28 ms of CPU and every eighth row about 5 ms; Moonraker's virtualenv Pillow `10.0.1` with libjpeg-turbo encoded the frame as a quality-75 JPEG (about 27 KB) in about 19 ms and as WebP in about 350 ms. `ffmpeg` fbdev capture with MJPEG encoding used about 66% of a core at 4 fps and about 130% at 10 fps.
- **Runtime-confirmed:** QIDI's nginx (`/etc/nginx/sites-available/fluidd`, CRLF line endings, not owned by a Debian package) serves Fluidd on ports 80 and 10088 with `--with-http_auth_request_module`, defines the `apiserver` upstream and `$connection_upgrade` map in `/etc/nginx/conf.d/`, and forwards `X-Real-IP`. Moonraker runs with `xheaders`, so `/access/user` answered 200 for a forwarded `192.168.1.50` and 401 for `8.8.8.8` under QIDI's default trusted ranges. QIDI's Moonraker also accepts loopback clients without authorization.
- **Runtime-confirmed:** on one Max 4 running `01.01.07.01`, QIDI's Moonraker uses the `systemd_dbus` provider and lists in Fluidd's service controls only `klipper*`, `moonraker*`, and loaded units named in `~/printer_data/moonraker.asvc`. QIDI's list (`qidi:netdev`, mode `0644`, no final newline) names `klipper_mcu`, `webcamd`, `MoonCord`, `KlipperScreen`, `moonraker-telegram-bot`, `moonraker-obico`, `sonar`, `crowsnest`, `octoeverywhere`, and `ratos-configurator`, but not `qidi-client`. Polkit is `0.105`, which has no per-unit rules, and `pkcheck` granted `org.freedesktop.systemd1.manage-units` to the `qidi` user. `qidi-client.service` is enabled, runs as root with `Restart=always`, and starts `/home/qidi/QIDI_Client/bin/start.sh`.

## Touchscreen Moonraker connection

- **Runtime-confirmed:** on one Max 4 running `01.01.07.01`, `qidiclient` connects to Moonraker directly at `127.0.0.1:7125` (user agent `WebSocket++/0.8.2`, registered as agent `QD_MAX4`), not through nginx.
- **Static-recovered:** in `qidiclient` SHA-256 `b5285d1a52f1180757360d0893f0f8ed619aaaa31d2d621917c0a963bc3fde4e` (`01.01.07.01`), a loop checks the Moonraker connection every 5 seconds and reconnects when it is down. After 10 consecutive failed reconnects it logs `检测到连接断开重连次数达到阈值，报错 MoonrakerError` ("reconnect attempts reached the threshold, reporting MoonrakerError") and sets its `moonrakererror` key; a successful connection resets the count. Ten failed subscription attempts instead report `KlipperError`.
- **Static-recovered:** the `QDC_400_005_015_001` handler subscribes to `moonrakererror`; its show predicate is always true and its clear predicate always false. `resource/qidi_client_error/QDC_400_005_015_001/0.json` titles it `Printer service failed to start` with `Please reinstall or contact customer support`.
- **Runtime-confirmed:** on that printer, `moonraker.service` has `Type=simple`, `Restart=always`, `RestartSec=10`, and `RemainAfterExit=yes`. - **Runtime-confirmed:** on that printer, Moonraker's process received SIGTERM outside systemd and exited within a second, while the unit stayed active until a `systemctl restart` 97 seconds later. `qidiclient`, running throughout, then showed `QDC_400_005_015_001` with **Restart Klipper** and **Restart Firmware** buttons and still showed it a day later while Moonraker and Fluidd worked normally.

## Moonraker speedups

- **Runtime-confirmed:** on one Max 4 running `01.01.07.01`, QIDI's Moonraker is a January 2024 tree without git metadata (API `1.4.0`, SQLite database) running in `~/moonraker-env` on Python 3.9.2. Its `utils/json_wrapper.py` uses `msgspec` and its `eventloop.py` uses `uvloop` when they import, unless `MOONRAKER_ENABLE_MSGSPEC` or `MOONRAKER_ENABLE_UVLOOP` is set to something other than `y`, `yes`, or `true`. Neither package is installed, and its startup log reports `msgspec_enabled: False` and `uvloop_enabled: False`.
- **Runtime-confirmed:** on that printer at idle, a py-spy profile of Moonraker's main thread spent its time on websocket writes and stdlib `json.dumps` of status updates; database work did not appear. Klipper sent one status update per second of about 12.5 KB, mostly the full `box_extras` Box list.
- **Runtime-confirmed:** on that printer at idle with two websocket clients and the same Klipper build, Moonraker used 5.6% of a core with neither package, 5.07% with `msgspec` 0.20.0, and 4.35% with `msgspec` and `uvloop` 0.23.0 (three 120-second windows each after a fresh restart). The full-status subscribe reply took 1198 ms, 1034 ms, and 864 ms. With both packages, Moonraker's JSON has no spaces after separators and replies are 3–16% smaller, the read methods Fluidd uses return the same keys and value types, and `qidiclient` kept reading Box status.

## Host memory and kernel

- **Runtime-confirmed (Max 4 test printer, `01.01.07.01`):** the host is an RK3308 (four Cortex-A35 cores, 486 MB RAM) running kernel `5.10.160 #4 SMP PREEMPT Wed Sep 3 15:21:57 CST 2025`, built with Arm GNU Toolchain 10.3-2021.07 `aarch64-none-linux-gnu`. It has swap support but no swap, no zram, zsmalloc, lz4, or lzo, no memory cgroup controller, no compaction, no PSI, no `MODVERSIONS`, no `/proc/config.gz`, and no `/proc/kcore`. `/lib/modules` holds only Wi-Fi and Bluetooth drivers. The boot partition is an Android boot image holding an LZ4-compressed `Image`.
- **Static-recovered:** `algo_app.service` sets `MemoryHigh=200M` and `MemoryMax=250M`; without the memory controller the kernel does not enforce them.
- **Runtime-confirmed (one user's printer, 2026-11-03, `ps` while printing with AI detection and timelapse on):** `algo_app` held 189 MB resident and 78% of a core, `qidiclient` 72 MB, Klipper 52 MB, and Moonraker 48 MB, leaving 24–35 MB available with `kswapd0` at 18% of a core. That printer's `klippy.log` showed available memory falling by about 90 MB about 4.6 minutes into every print, and two prints cancelled while printing ended in `Missed scheduling of next digital out event` shutdowns after Klipper's process stopped for 11 s and about 2 min 46 s.
- **Runtime-confirmed (test printer, idle Klipper, a test process holding 215 MB of 2:1-compressible memory then 60 MB more):** without swap the test process was OOM-killed, Klipper's longest timer delay was 405 ms, and Klipper took 2,707 major page faults. With 256 MB of lz4 zram swap, nothing was killed, the longest delay was 4 ms, and Klipper took 36 major page faults. With zram, swappiness 60 against 80 against 100 gave longest delays of 4, 4, and 2–145 ms at the 60 MB spike, and 189, 3, and 16 ms with a 120 MB spike; at 60 with the larger spike the system took 37,808 major page faults.
- **Runtime-confirmed (test printer):** Debian's `cpufrequtils` service sets the `ondemand` governor at boot from its script default, reading `/etc/default/cpufrequtils` when present; the printer has no such file. The RK3308BS operating points are 408 MHz at 0.85 V, 600 MHz at 0.90 V, 816 MHz at 1.00 V, 1008 MHz at 1.125 V, and 1104 MHz at 1.20 V. `ondemand` samples every 10 ms with `up_threshold` 95. The SoC thermal zone has passive trips at 70 °C and 85 °C, with the CPU frequency cooling device bound to 85 °C (step-wise), and a critical trip at 115 °C.
- **Runtime-confirmed (test printer, Klipper's step generation for CoreXY with an MZV shaper in 0.1 s windows, run between idle gaps):** at room temperature a burst took 5.5–6.3 ms under `ondemand` and 3.3–3.4 ms under `performance` after 20–500 ms idle, and 3.5–3.6 ms under both when sustained; idle Klipper used 31.8% against 26.1% of a core. With the chamber held at 65 °C and that load every 100 ms, the SoC averaged 71.8–72.2 °C under `ondemand`, 72.1 °C under `ondemand` with an 816 MHz floor and `up_threshold` 50, and 73.2 °C under `performance`, peaking at 74.4 °C; nothing throttled. Bursts after idle took 5.4–6.4 ms, 4.3–4.7 ms, and 3.4–3.7 ms respectively.
- **Runtime-confirmed (test printer):** lz4 compressed 64 MB of Klipper and Moonraker files 2.3:1 at 47 MB/s and decompressed at 162 MB/s through `/dev/zram0`; lzo-rle gave 2.5:1, 52 MB/s, and 127 MB/s.

## Stock integration constraints

- `config/fluidd.cfg` is printer-owned and read-only for this repository.
- Stock QIDI macro names are consumed by Fluidd, QIDI Client, and vendor modules even when optimized wrappers supersede their behavior.
- `G4 P...` adds fixed dead time; `M400` waits only for queued motion.
- Stock globals with no repository caller may still be consumed by vendor components.
- Config-confirmed QIDI Max 4 machine profiles installed with OrcaSlicer and QIDI Studio move to absolute `Z10` after `M1002 A1`, then apply `G92_ Z{10 - ((nozzle_temperature_initial_layer[initial_tool] - 130) / 14 - 5.0) / 100}` before first-layer priming.
