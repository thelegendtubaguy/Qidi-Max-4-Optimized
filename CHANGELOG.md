# Changelog

## 26.11.06.1
- New `TLTG_CUT_FILAMENT` cuts the filament at the toolhead without heating the nozzle, for example to free Box filament caught in the hub from Fluidd. The QIDI Box card in Fluidd has a new **Cut** button that runs it. To keep the card's slot actions on one row, **Read RFID** and **Edit** are now icon buttons beside the slot's label, and the jog buttons are a joined **In**/**Out** pair. On the Max 4 the cutter cuts cold filament and the extruder sits above the cutter, so the extruder's 4 mm pull-back after the cut moves only filament that never enters the hotend. Klipper refuses every extruder move, pull-backs included, below `min_extrude_temp` (135 °C), so QIDI's `CUT_FILAMENT_1` run cold cut the filament, then stopped with `Extrude below minimum temp` and left the acceleration it had raised. During the new cut, pull-backs are allowed and pushing filament forward is still refused; afterwards Klipper's check is back as it was. The cut homes X and Y first if either isn't homed, puts the acceleration and positioning mode back even if it stops with an error, and is refused while a print is running or paused or the Box is busy. See [Cutting the filament](docs/qidi-box.md#cutting-the-filament).
- QIDI Box unloads and ejects can now run without heating the nozzle: `UNLOAD_FILAMENT_CONTROL SLOT=<n> COLD=1` and `EJECT_FILAMENT_CONTROL SLOT=<n> COLD=1`. QIDI's heat the nozzle to the top of the filament's printing range first, 280 °C for some ASA, though nothing in them needs the heat. With `COLD=1` the same steps run with the heater off, pull-backs allowed as for the cut, and without QIDI's 5 second wait and nozzle wipe at the end; **Retry** of a failed step stays cold. `COLD=1` is refused during a print, and an unload that would also unload the external spool still heats and says so. **Unload** and **Eject** on the QIDI Box card in Fluidd now send `COLD=1`, except while a print is paused. Without `COLD=1` the commands are unchanged. Fluidd is updated to v1.37.7-tltg-b625096. See [Unloading and ejecting cold](docs/qidi-box.md#unloading-and-ejecting-cold).
- `OPTIMIZED_CUT_FILAMENT` run by hand now homes X and Y first when either isn't homed, instead of failing with `Must home axis first`. The cut copied QIDI's `_CG28`, which isn't defined in QIDI's configuration or Klipper, so it never homed.
- The QIDI Box's default extruder pull-back at the start of an unload is now 55 mm instead of 50 mm. On one Max 4, the filament once left the toolhead sensor only as a 50 mm pull ended, where on another it left 4 mm in; 55 mm keeps some margin. Updating raises a pull-back still at 50 mm to 55 mm and keeps one you've changed. QIDI's is 120 mm; if unloads fail with `QDE_004_008` (`Extruder unloading failure.`) and nothing is caught between the Box and the toolhead, set it back with `TLTG_BOX_MOTION UNLOAD_EXTRUDER_LENGTH=vendor`. See [Load and unload speed](docs/qidi-box.md#load-and-unload-speed).
- Fixed Fluidd's QIDI Box card saying the external spool was loaded while a Box slot was feeding the toolhead, during prints and during failed unloads. QIDI leaves its record of the slot driving the extruder empty at those times, and the card took filament at the toolhead with no slot recorded to be the external spool's. Box filament passes the Box hub's sensor and the external spool's doesn't, so with filament at the hub the card now shows the Box slot at the hub.
- Fluidd now labels the exhaust fan **Chamber Exhaust Fan**. QIDI's config names it `chamber_circulation_fan`, so Fluidd showed it as Chamber Circulation Fan. Only the label changes. Fluidd is updated to v1.37.7-tltg-b625096.
- Fixed QIDI Box loads, unloads, and ejects failing at every heat step with `Move out of range`, such as `Move out of range: 121.000 753.000 0.000 [-1924.000]`, until Klipper restarted. QIDI's park over the waste chute assumes absolute positioning but doesn't set it, so relative positioning left on by an earlier command, such as one that stopped with an error before switching back, sent the park off the bed. A load, unload, or eject started or retried with no print running or paused now switches to absolute positioning first, as `G90` does; during a print, positioning is left as the print set it. See [Failed Box loads and unloads](docs/qidi-box.md#failed-box-loads-and-unloads).
- Fixed `Timer too close` lines in `klippy.log` on the Max 4, nearly all of them while homing X and Y. QIDI's Klipper turns a motor on 0.3 seconds before it moves, so it holds position first, but after homing turns X and Y off, the first homing move starts only about 0.16 seconds ahead, so the turn-on was scheduled in the past and the mainboard ran it late. The motor now turns on as early as it still can, about 0.14 seconds before the move during homing, and otherwise exactly as before. Homing itself is unchanged. See [Fixes for QIDI bugs](docs/fixes.md#motors-turning-on-late).
- `klippy.log` now names the cause of any other late command. When Klipper sends a board a command, such as a pin or fan change, whose time has already passed, it logs a `late MCU command` warning with the board, the command, how late it was, and the code that sent it, at most once every 10 seconds per command. A few `Timer too close` lines during prints still have no known cause; this is how the next one will show it.
- New on the Max 4: an optional X/Y step-loss monitor that pauses the print when an X or Y motor slips. QIDI's closed-loop X and Y motors know how far they are behind where they were told to be, but QIDI's software never asks, so a motor that slipped against a curled part or a binding belt stayed behind for the rest of the print without any warning; on the test printer, a 14 mm slip left the motors reporting a normal status. With `SAVE_VARIABLE VARIABLE=tltg_step_loss_monitor VALUE=1`, a new module, `tltg_step_loss_monitor`, asks each motor about twice a second, while X and Y are homed, how far it is from where it stood after homing. A slip of at least three quarters of a step cycle (0.59 mm of belt) on two checks in a row pauses a running print, and the console and Fluidd's warning banner name the motor and how far it slipped until X and Y are homed again. The monitor only reads the motors' position; it changes no motor setting. It's off by default. See [X/Y step-loss monitor](docs/tools.md#xy-step-loss-monitor).
- The Max 4's top speed is now 565 mm/s instead of QIDI's 800, so the X and Y motors no longer skip on fast diagonal moves. QIDI's limit applies to the toolhead, but on a CoreXY a diagonal move turns one motor up to 1.41 times as fast, about 1130 mm/s of belt at 800 mm/s; on the test printer, back-and-forth diagonals at 800 mm/s made the X motor skip about 60 mm of belt with a loud grinding, while nothing skipped at 500 mm/s. 565 mm/s keeps every motor at or below 800 mm/s of belt in any direction. Install and update change `max_velocity` in `printer.cfg` from 800 to 565. Moves between bed mesh and leveling points now run at 565 mm/s instead of 600, and the travel to the Z-home point and to the leveling start at 565 mm/s instead of 750 and 600. Any `max_velocity`, bed mesh `speed`, or Z-tilt `speed` above 565, including one you set yourself, is lowered to 565; lower values are kept, and uninstall puts back the values you had. A new module, `tltg_velocity_limit`, holds `SET_VELOCITY_LIMIT VELOCITY=`, and QIDI's `M203` that uses it, to `max_velocity`, with a console note, as QIDI's Klipper already holds acceleration to `max_accel`. Slicer speeds up to 565 mm/s, including the 500 mm/s travel in QIDI's Max 4 profile, are unchanged. See [X/Y motors skipping at top speed](docs/fixes.md#xy-motors-skipping-at-top-speed).

## 26.11.05.1
- The project is now called Valve Oil and lives at `https://github.com/thelegendtubaguy/valve-oil`. Links to the old address redirect, and the installer and automatic updates now download from the new one, so there's nothing to do. The installer shows the new name; macro names, files on the printer, and slicer profiles are unchanged.
- The installer now checks which printer it's on as well as its firmware version. QIDI's firmware manifest names the printer model in its file name, and if that model doesn't match the firmware version, the installer stops with `Your firmware version is not supported.` before changing anything. This prepares for supporting printers other than the Max 4; nothing changes on a Max 4.
- The optimized macros now keep the printer's own homing, filament cutter, wiper, waste chute, and rear-bed scrape moves, bed-screw positions, and default input shaper calibration apart from the rest, in three new files in `config/tltg-optimized-macros/`: `homing.cfg`, `nozzle_motion.cfg`, and `printer_profile.cfg`. The installer picks them for the printer it detects. This prepares for printers other than the Max 4; macro names and what the Max 4 does are unchanged, and updating replaces the old files.
- Every install and update now applies the OS optimizations, including automatic updates and printers where an earlier install skipped them. The printer has little memory and CPU to spare, and each release is tested with zram swap, the full-speed CPU, the storage repair, and the rest of the OS optimizations on, so leaving them off is no longer an option. The installer no longer asks `Would you like to apply system hardening and OS optimizations?`, and `--skip-system-optimizations` is gone. Its only remaining OS question is whether to turn off QIDI AI detection, asked only while AI detection is on; `--yes` installs and automatic updates keep your earlier answer, and `--disable-ai-detection` and `--keep-ai-detection` still answer it ahead of time. Uninstall still asks whether to undo the OS optimizations. See [OS optimizations](docs/install.md#os-optimizations).
- The OS optimizations now turn off ADB. QIDI's system image runs ADB as `root` on TCP port 5555 with no authentication, so anyone on the printer's network could get a root shell without a password, whatever the `qidi` password is. It comes from `usbdevice.service`, a Rockchip board-image leftover whose only function is ADB; nothing QIDI ships uses it, and the USB port for flash drives keeps working. Install and update stop and disable it, and uninstall asks before turning it back on, as for the other OS optimizations. See [ADB](docs/install.md#adb).
- When the OS optimizations need a reboot, the printer now reboots by itself instead of asking. An install, interactive or `--yes`, reboots about 10 seconds after it finishes unless a print is running or paused, and checks again just before rebooting; `--reboot-host` is no longer needed for installs. An automatic update reboots only once Klipper has been idle for 10 minutes, with no print running or paused, no command running, the toolhead still, and every heater, including the Box dryers, off; until then, each hourly check tries again. Before, automatic updates never rebooted for zram swap, the CPU setting, or the service priorities.
- When a homing or probe move fails with `Communication timeout during homing` or the nozzle load-cell probe's `WEIGHT sensor error`, the console now also says which board's sync timed out and how far apart each board sent its status reports and Klipper received them. A move that involves both the toolhead board and the mainboard stays armed only while each board's status reports, every 15 ms, keep reaching Klipper, and Klipper's serial threads, not its main thread, pass them on. So the main-thread figures the message already gave could show nothing wrong while a sync timed out, as on two printers whose first bed-mesh probe or first Z home failed this way. Reports sent far apart point at the board; reports sent on time but received far apart point at the connection or the printer's own CPU. `klippy.log` also gets each board's last reports. The error itself and what happens to the print are unchanged. See [Klipper slowing down during long Box prints](docs/fixes.md#klipper-slowing-down-during-long-box-prints).
- Fixed the camera sometimes disappearing from Fluidd after a reboot. At boot, QIDI's `makerbase-webcam.service` sets the camera in `crowsnest.conf`, but it could look for the camera's device link a fraction of a second before the system created it, and then wrote an empty `device:` line. Crowsnest, which streams the camera, then stopped with `Parameter device not found`, and Fluidd showed no camera until the line was fixed by hand. Install and update now make QIDI's script wait up to 30 seconds for the camera; if it never appears, the script is skipped and the camera setting is left as it was. A printer that already lost its camera gets it back at its next reboot. See [The camera doesn't show in Fluidd](docs/troubleshooting.md#the-camera-doesnt-show-in-fluidd).

## 26.11.04.1
- Turning on the exhaust fan no longer turns off the chamber heater. QIDI's `M106` set the chamber target to 0 whenever `M106 P3` set the exhaust fan above 0, so a filament profile with its exhaust fan (air filtration) on during the print stopped heating the chamber when the fan came on, without saying so. The heater now keeps its target, and when the exhaust fan turns on while the chamber heats, the console warns with the fan speed and chamber target and says to turn off the profile's exhaust fan to heat the chamber fully. The exhaust pulls heat out of the chamber, and if the chamber stays more than 5 °C below its target for long, or stops gaining while it heats, Klipper stops the print with `Heater chamber not heating at expected rate`. Before that can happen, a new module, `tltg_chamber_exhaust_guard`, turns the exhaust fan off for the rest of the print and says so in the console: when a chamber that had reached its target falls back to 4 °C below it, or when one still heating has gone 4 minutes without gaining 1 °C. Later requests to turn the exhaust on during that print are ignored while the chamber heater is on; the end-of-print exhaust still runs. Install and update replace QIDI's `M106` in `klipper-macros-qd/fans.cfg`; the other fans work as before. See [Exhaust fan while heating the chamber](docs/print-start.md#exhaust-fan-while-heating-the-chamber).

## 26.11.03.1
- Uninstall now undoes the storage repair from the OS optimizations after the printer has been updated. Before, any later install or automatic update recorded the repair without the mount state uninstall checks, so uninstall reported "Rockchip system state was modified after install and was preserved" and left the repair in place. Printers that already have that record are fixed on their next update.
- Fluidd now takes less of the printer's CPU to load. Fluidd is updated to v1.37.7-tltg-c1b7d04, which includes a ready-compressed copy of each script, stylesheet, and image, and nginx sends those instead of compressing each file on every request. QIDI's setup compressed scripts and stylesheets as it sent them, which took the printer 0.74 s for Fluidd's largest script alone and about 3.5 s for the whole set; it now takes no compression time, and images are compressed too. The installer download is about 3 MB larger.
- The installer now says what it's doing while it makes its system changes, naming each change and each service it restarts. Before, a first install showed nothing for about a minute and a half after the AI detection question, and uninstall went quiet the same way. The reminder to turn off Spaghetti Detection and Foreign Object Detection on the touchscreen now comes after those changes, once the touchscreen app has restarted, instead of before them. It now also shows for `--yes --disable-ai-detection` installs. The system changes are also faster. The repair that stops QIDI's boot service from making the printer's storage write synchronously now runs first instead of last, so the other changes write their files faster. Adding the Printer screen and zram services now reloads systemd once instead of twice per service; each reload takes 2–3 s on the printer. On the test printer, a first install's system changes took 75 s instead of 93 s, and uninstall's took 47 s instead of 73 s.
- When the nozzle load-cell probe fails with `Error during homing probe: WEIGHT sensor error`, the console now also says which boards were involved and how busy Klipper was just before, as it already did for `Communication timeout during homing`. QIDI's probe reports a timed-out probe move as `WEIGHT sensor error`, and the toolhead board's firmware never reports an actual load-cell fault that way, so the message almost always means the toolhead board and mainboard lost sync during the probe move, not a faulty load cell. The error itself and what happens to the print are unchanged. See [Klipper slowing down during long Box prints](docs/fixes.md#klipper-slowing-down-during-long-box-prints).
- The OS optimizations now give the printer compressed swap in memory (zram). The printer has 486 MB of memory and no swap, and QIDI's AI detection alone can hold about 190 MB during a print. When memory ran out, Linux made room by dropping program code and reading it back from storage, which stalled Klipper for seconds at a time; one printer's prints ended with `MCU 'mcu' shutdown: Missed scheduling of next digital out event` right after they were cancelled. With memory filled the same way on the test printer, Klipper's longest delay went from 405 ms to 4 ms, and the program filling memory was no longer killed. QIDI's kernel has no zram, so the package carries modules built for QIDI's exact kernel; they load on no other kernel, so a QIDI update that changes the kernel runs without zram. Swap is 256 MB, lz4-compressed, with `vm.swappiness` 80 and `vm.page-cluster` 0. Uninstall asks before turning it off, as for the other OS optimizations. See [Zram swap](docs/install.md#zram-swap).
- The OS optimizations now run the CPU at full speed. QIDI's `ondemand` setting raised the clock only when the CPU was more than 95% busy for 10 ms, which Klipper's short bursts of work rarely are, so most of them ran at 408–600 MHz instead of 1104 MHz. Bursts of Klipper's step generation after a pause now take about 3.4 ms instead of 5.5–6.4 ms, and idle Klipper uses about 18% less CPU. With a 65 °C chamber, the processor ran about 1 °C warmer, at 73 °C, and the kernel only slows it down at 85 °C. Uninstall asks before putting `ondemand` back, as for the other OS optimizations.
- Klipper now gets the CPU before Moonraker, and both before QIDI's touchscreen app, instead of all three sharing it equally. Each restarts once to pick up its new priority. See [Klipper sharing the CPU with the touchscreen](docs/fixes.md#klipper-sharing-the-cpu-with-the-touchscreen).
- Flashing the optional THR FIFO fix no longer clears your input shaper calibration from `printer.cfg`. Before-and-after testing showed the fix changes calibration results only slightly, so the saved calibration now stays in use. The installer still asks you to rerun input shaper calibration, now before bed leveling as well as printing.
- When an axis has no input shaper, for example because no calibration is saved, Klipper now gives it QIDI's stock calibration (EI at 54.4 Hz on X, MZV at 36.2 Hz on Y) at startup and after every X/Y home, before the toolhead moves to home Z. Until a calibration is saved, homing keeps acceleration at QIDI's 10000 mm/s² instead of the full 30000, and the console warns at startup and after every home to run input shaper calibration. Without any input shaping, full-speed leveling and bed mesh moves can shake the toolhead hard, and some printers may skip belts or lose position. This can happen after the THR FIFO fix cleared the calibration in earlier versions, especially from the touchscreen's calibration page, which runs bed leveling before input shaping when both are checked. Nothing is written to `printer.cfg`, so your own calibration replaces QIDI's as soon as it runs, and the next home goes back to full acceleration without a restart. Accelerations your slicer sets during a print are not limited, and no slicer G-code changes are needed. See [No input shaper calibration](docs/print-start.md#no-input-shaper-calibration).
- Fluidd now shows problems to fix before printing, starting with a missing input shaper calibration, in a red banner under the top bar on every page. It stays in view as you scroll, can't be closed, and goes away by itself once the problem is fixed. See [No input shaper calibration](docs/print-start.md#no-input-shaper-calibration).
- After an install that turns on zram swap, the full-speed CPU setting, or the service priorities, the installer offers to reboot the printer, checking first that nothing is printing. They already run without one; the reboot shows they start on their own. `--yes` installs only say to reboot unless `--reboot-host` is given, and automatic updates never reboot for this.

## 26.11.02.1
- Running the installer with `sudo` now gives the same result as running it as `qidi`. Before, `sudo` ran everything as root: every file the installer created, such as its lock, its record of what it installed, its backups, and its Klipper modules, belonged to root, and `sudo /bin/bash -c "$(curl …)"` unpacked the installer in `/root`, where `qidi` can't reach it. Automatic updates turned on during such a run also ran as root from then on. A later run without `sudo` then stopped with `[Errno 13] Permission denied: '/home/qidi/printer_data/.tltg_optimized_installer.lock'` or `Could not validate previous package version.` The installer, `install-latest.sh`, `restore.sh`, `auto-update.sh`, and `box-firmware.sh`, including the toolhead board firmware fix, now switch to `qidi`, the owner of `~/printer_data`, when started as root, and use `sudo` themselves for the steps that need it, as they do without it. `install-latest.sh` unpacks into `/home/qidi`, and an installer in `/root` copies itself there first. Automatic updates turned on from a root run go back to running as `qidi` at the next install or update.
- Every run now first gives the installer's own files that an earlier run as root left owned by root back to `qidi`, and says how many it changed. Those are everything named `tltg` in `~/printer_data`, `~/printer_data/config`, the home folder, and Klipper's `klippy/extras`, along with everything inside them. QIDI's own files, some of which QIDI ships owned by root, are left alone. A printer with a mix of root-owned and `qidi`-owned files is fixed by updating, with or without `sudo`. See [The installer stopped](docs/troubleshooting.md#the-installer-stopped).
- Fixed Klipper slowing down over long QIDI Box prints. Each Box load left three of QIDI's timers behind, from the load-cell check that confirms the filament reached the nozzle, and Klipper checks every timer many times a second. After about 400 filament changes in a multi-day print, Klipper was busy most of the time even while idle, and a Box unload failed with `Error during homing b_endstop: Communication timeout during homing`, which cancelled the print. A new module, `tltg_klipper_health`, removes those timers once QIDI is done with them. It also warns in the console if Klipper's timers keep piling up or Klipper stays more than 45% busy for five minutes, says how busy Klipper was when a homing move times out, and logs Klipper's timer count and load to `klippy.log` every minute. See [Klipper slowing down during long Box prints](docs/fixes.md#klipper-slowing-down-during-long-box-prints).
- Fluidd's **System Utilization** card on the System page now charts **Klipper Timers**, the number of timers Klipper is running, and adds a **Klipper Main Thread** line under Klipper Load. Klipper Load counts all of Klipper's threads; the main thread is the one that has to keep up with the printer, and a Box motor move can fail with `Communication timeout during homing` when it has no headroom left. The timer count stays around 60; one that keeps climbing slows Klipper down. See [Klipper slowing down during long Box prints](docs/fixes.md#klipper-slowing-down-during-long-box-prints).
- Klipper does less work on its main loop during QIDI Box prints, leaving Box motor moves more headroom. QIDI's Box modules saved their own settings by rewriting `saved_variables.cfg` in place and reading it back, even when nothing changed: about 20 saves at Box print start, which held Klipper for about 1.3 seconds, and about 8 in every filament change. They now skip saves that change nothing and replace the file whole, as `SAVE_VARIABLE` already did, so a power cut during a save can't leave it half written. The optimized filament-change, temperature-wait, and homing macros no longer copy QIDI's whole Box and configuration status each time they run, which held Klipper for 10–50 ms. QIDI's Box status, which Fluidd and the touchscreen read every second, takes about half as long to build, and Spoolman's slot tracking no longer builds it twice a second. Every macro, QIDI's included, reads printer settings and status faster, including QIDI's start-up macro, which held Klipper for about 0.8 seconds after every start. Until RS-485 hardware has been seen, QIDI's software looks for an RS-485 adapter every 30 seconds instead of every 2, so a newly connected adapter can take up to 30 seconds to be found. Klipper's check of its timers, which runs many times a second, takes about a third less time, and QIDI's once-a-second status update for Fluidd and the touchscreen skips macros whose values haven't changed and compares the Box status faster, sending the same updates. See [Klipper slowing down during long Box prints](docs/fixes.md#klipper-slowing-down-during-long-box-prints).
- Brought in later fixes from upstream Klipper, applied to QIDI's Klipper when it starts. Homing moves, including the Box's, set up their endstop sync for the start of the move instead of after the move's own step messages. A Box or toolhead board that restarts by itself stops Klipper with `MCU '…' spontaneous restart` instead of failing later with another error. Commands waiting on a Box or board that Klipper has lost contact with fail with `No communication with MCU` instead of waiting forever and holding up every later command. Heaters turn off if Klipper's main loop stops for 5 seconds, a heater's temperature reads 0 only 7 seconds after its last reading instead of 5, a stepper disable waits for an unfinished driver enable, and a Klipper timer can't run twice at once. Python's garbage collector also skips what Klipper set up at startup. `klippy.log` lists the fixes applied. See [Fixes from newer Klipper](docs/fixes.md#fixes-from-newer-klipper).
- A filament change during a print that ends with an error, such as `Communication timeout during homing` from a Box motor move, now pauses the print instead of cancelling it, as QIDI already did when a step failed. The console says which tool and step failed and why, and **Resume** finishes the filament change and carries on printing. A Klipper shutdown, such as a lost Box connection, still ends the print. See [Failed tool changes during a print](docs/qidi-box.md#failed-tool-changes-during-a-print).
- Fixed **Resume** failing with `Extrude below minimum temp` after a pause with the QIDI Box, leaving the print paused until the nozzle temperature was set by hand. Pausing turns the nozzle off, and QIDI's Box resume cuts the filament, which pulls it back a little, before heating the nozzle again, so once the nozzle had cooled below 135 °C the cut failed and nothing else ran. **Resume** now moves to the waste chute and heats the nozzle to the temperature it had when the print paused before QIDI's resume starts. See [Resuming a paused print](docs/qidi-box.md#resuming-a-paused-print).
- When an OS optimization fails and undoing it fails too, the installer now says what failed first. Before, it showed only the undo's failure, such as `System optimization rollback failed: Moonraker did not answer after its restart.`, so the problem that started it was lost. It now shows `System optimization failed:` with the first error, then `Rolling it back also failed:` with the second. The next run, which finishes the undo, also says what the earlier run failed with, and says it finished, instead of `Pending Rockchip system transaction recovered.`, which it showed for any unfinished change, not only Rockchip ones.
- Moonraker uses less CPU. QIDI's Moonraker already uses `msgspec` to build the JSON it sends to Fluidd and the touchscreen, and `uvloop` to run its event loop, when they're installed, but QIDI doesn't install them. The installer now adds them in `~/tltg-moonraker-speedups`, from the release bundle, without replacing anything in QIDI's `~/moonraker-env`, and restarts Moonraker. On the test printer at idle, Moonraker went from 5.6% to 4.35% of a CPU core, sending a full status to a newly connected Fluidd took 0.86 seconds instead of 1.2, and Moonraker's replies got 3–16% smaller. Fluidd and the touchscreen work as before. Moonraker's JSON no longer has spaces after `:` and `,`, so a script that searches its replies for text such as `"state": "printing"` needs to allow for that. Uninstall removes them. See [What the installer changes](docs/under-the-hood.md#klipper-and-moonraker-source-and-services).

## 26.11.01.1
- Fixed Klipper failing to start with `Permission denied` (`Errno 13`) on the project's Klipper modules, `klippy/extras/tltg_*.py`. Install and update created each new module readable only by the user who ran them, so a printer installed as root, whose automatic updates then also ran as root, wrote modules Klipper couldn't read. Fluidd and the touchscreen then couldn't connect, and only SSH worked. A QIDI firmware update removes the modules, and the next automatic update recreated them the same way. Modules are now readable by every user, and updating fixes modules an earlier version installed.
- `T0` through `T15`, including the tool buttons in Fluidd's Tool card, now run only while a print is running or paused. They are QIDI's print-time tool change, which cuts, unloads, and loads without heating the nozzle; outside a print it ran with the nozzle cold or cooling, failed with `Extrude below minimum temp`, and could leave the QIDI Box card stuck loading and the printer paused with no print. Outside a print nothing moves, and the console says to use **Load** on the QIDI Box card or `LOAD_FILAMENT_CONTROL SLOT=<n>`. ## 26.10.29.1
